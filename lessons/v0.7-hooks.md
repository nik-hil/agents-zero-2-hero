# v0.7-hooks — Lifecycle hooks

> **Pillar:** 🛡️ Governance
> **Adds:** `HookManager` with PreToolUse / PostToolUse hooks
> **Builds on:** `v0.6-permissions`

## The idea

Permissions (v0.6) answered one question: *is this tool call allowed?* Hooks
answer a different one: *what else should happen around it?* — logging, metrics,
redacting secrets from output, or extra custom blocking — all **without editing
the tools or the loop**. It's the extension point that keeps the core small.

Two moments fire around every tool call:

- **PreToolUse** — before the tool runs. Can observe, **rewrite the args**, or
  **block** the call.
- **PostToolUse** — after the tool runs. Can observe or **rewrite the result**.

## How this fits with permissions

The loop runs them in a deliberate order (see `coding_agent.py`):

```
permission check  →  pre-hooks  →  execute tool  →  post-hooks
   (hard gate)        (custom)                        (custom)
```

Permissions are the fixed safety gate; hooks are *your* pluggable behavior layered
on top. A pre-hook can add its own block (e.g. "no bash today"), but it can't
loosen a permission denial — that already happened first.

## How to understand this lesson

1. **`hooks.py`** — read `HookResult` and `HookManager` first. `run_pre` threads
   the args through each pre-hook (so one hook can rewrite what the next sees) and
   stops if any blocks; `run_post` threads the result through each post-hook.
   Then skim the example hooks: `TimingLogger`, `make_counter`, `block_tool`,
   `redact_post_hook`.
2. **`coding_agent.py`** — find the `1) / 2) / 3)` comments in the tool loop to
   see exactly where pre/post fire, and how the `__main__` demo attaches a timing
   logger + a usage counter.
3. **`tests/test_hooks.py`** — each test is a one-line spec: block, rewrite args,
   run in order, count, redact.

## What the example hooks actually do (annotated)

When you run `python coding_agent.py`, `__main__` registers two hooks:

```python
timer = TimingLogger()
tool_counts = {}
hooks = HookManager(
    pre=[timer.pre],                      # runs before every tool
    post=[timer.post, make_counter(tool_counts)],  # both run after every tool
)
```

Here's what each one does, matched to the output you saw:

**1. `TimingLogger` — a class holding shared state across pre and post.**
It remembers when a tool started so `post` can measure how long it took.

```python
class TimingLogger:
    def __init__(self):
        self._start = {}                       # tool name -> start time

    def pre(self, tool, args):
        self._start[tool] = time.perf_counter()  # stopwatch START
        print(f"  [hook] → {tool}({args})")      # the "→" line
        return None                              # None = don't block, don't rewrite

    def post(self, tool, args, result):
        dt = time.perf_counter() - self._start[tool]  # stopwatch STOP
        print(f"  [hook] ← {tool} done in {dt*1000:.1f} ms")  # the "←" line
        return None                              # None = leave the result as-is
```

So this line in your run —

```
Tool call: write_file with args: {...}      # printed by the loop
  [hook] → write_file({...})                # timer.pre  (stopwatch starts)
  [hook] ← write_file done in 1.3 ms        # timer.post (stopwatch stops)
Tool result: {...}                          # printed by the loop
```

— is the pre-hook firing, the tool running, then the post-hook firing. Returning
`None` is the important part: the hook only *observes*; it doesn't block the call
or change the args/result.

**2. `make_counter(tool_counts)` — a post-hook that tallies usage.**

```python
def make_counter(counts):
    def _hook(tool, args, result):
        counts[tool] = counts.get(tool, 0) + 1   # +1 each time this tool runs
        return None
    return _hook
```

It closes over the `tool_counts` dict you passed in and bumps a count on every
call. After the run, that dict is exactly what got printed:

```
Tool usage (from counter hook): {'list_files': 1, 'write_file': 1, 'read_file': 1, 'finish': 1}
```

**Who calls these?** The loop, via the manager. `hooks.run_pre(tool, args)` walks
the `pre` list before executing; `hooks.run_post(tool, args, result)` walks the
`post` list after. That's why `timer.post` (index 0) prints its line *before*
`make_counter` (index 1) bumps the tally — post-hooks run in registration order.

**The two hooks in your run didn't block or rewrite anything** (both return
`None`). The *power* of hooks is that they *could*: a pre-hook returning
`HookResult(allow=False, ...)` stops the tool (you'd see "blocked by hook"), and a
post-hook returning `HookResult(result=...)` swaps the output (that's what
`redact_post_hook` does to mask API keys).


Experiments: register `block_tool("write_file")` as a pre-hook and watch writes
get blocked *by a hook* (distinct from plan mode); add a post-hook that appends a
timestamp to every result.

## Takeaways

- Hooks are the "middleware" of the harness: cross-cutting behavior without
  touching tools.
- Pre-hooks can **observe, rewrite, or block**; post-hooks can **observe or
  rewrite**.
- Order matters — permission gate first, then hooks; pre-hooks chain their args.
