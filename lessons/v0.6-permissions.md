# v0.6-permissions — Permission modes

> **Pillar:** 🛡️ Governance
> **Adds:** `PermissionChecker` (auto / default / plan + path & command rules)
> **Builds on:** `v0.5-multi-provider`

## The idea

Back in v0.3 the `bash` tool had its own allowlist. That logic doesn't belong
inside one tool — it belongs in **one gate that every tool call passes through
before it runs**. The model still decides *what* to do; the harness decides
whether it's *allowed*. This is the difference between a toy and something you'd
let loose on a real repo.

## How to understand this lesson

Read the pieces in this order:

1. **`permissions.py`** — the whole feature lives here. Start at the `Mode` enum
   and `READ_ONLY_TOOLS`, then read `PermissionChecker.check()` top to bottom.
   It applies checks in three layers:
   - **hard rules** (denied commands, path rules) — enforced in *every* mode,
     even `auto`;
   - **read-only tools** (`list_files`, `read_file`, `code_search`, `finish`) —
     always allowed;
   - **mode** — governs only the *mutating* tools (`write_file`, `edit_file`,
     `execute_code`, `bash`).
2. **`coding_agent.py`** — see how the loop calls `permissions.check(tool, args)`
   *before* executing, and turns a denial into an error result the model can read
   (search for `Permission gate`).
3. **`tests/test_permissions.py`** — each test is a tiny spec of one rule; read
   them as executable documentation.

The three modes:

| Mode | Mutating tools | Use when |
|------|----------------|----------|
| `auto` | allowed | sandboxed / trusted runs (keeps the earlier demos working) |
| `default` | ask an approver (y/N) | day-to-day; you approve each write |
| `plan` | blocked | review-only; explore with zero side effects |

## Who decides — and a caveat about the lists

**The harness has the final say.** The model can only *request* a tool call;
`check()` runs *before* execution. So in `plan` mode (or when your approver says
no in `default` mode) the write simply never happens. The model proposes, the
harness disposes — permissions are entirely under your control, not the model's.

**The tool lists are not shared, and that matters.** Two files keep separate
lists, maintained by hand:

- `coding_agent.py` owns `TOOLS` — *what tools exist*.
- `permissions.py` owns `READ_ONLY_TOOLS`, `denied_commands`, and the
  `PATH_ARG` / `TEXT_ARG` maps — *how each tool is judged*.
- (`bash` also has its own v0.3 `ALLOWED_COMMANDS` allowlist — a third,
  independent layer.)

If these drift apart:

- A tool in `TOOLS` but **not** in `READ_ONLY_TOOLS` is treated as **mutating** —
  fail-safe: an unclassified tool gets *more* restricted, never less.
- But a genuinely read-only new tool you forget to list is wrongly blocked in
  `plan` mode (annoying, not unsafe).
- And if a new tool takes a path/command argument not in `PATH_ARG` / `TEXT_ARG`,
  the path rules and denied-command checks silently **don't apply** to it — a
  real gap to watch for.

The safe direction is automatic; the unsafe direction (a mutating argument the
checker doesn't know to inspect) is the one to guard. A cleaner design for a
later lesson: have each tool **self-declare** whether it's read-only and which of
its args are paths/commands, so there's one source of truth instead of two lists
that can diverge.

## Try it

```bash
# Read-only exploration — every write is refused:
AGENT_PERMISSION_MODE=plan python coding_agent.py

# Approve each mutating call yourself:
AGENT_PERMISSION_MODE=default python coding_agent.py

# Offline unit tests (always run):
python -m unittest tests.test_permissions -v

# End-to-end proof with a real model (skipped if no key):
python -m unittest tests.test_agent_integration -v
```

Experiments to build intuition: add `("*.env", False)` to a checker's
`path_rules` and watch reads of `*.env` get denied; add a phrase to
`denied_commands` and see a matching `bash`/`execute_code` call blocked even in
`auto` mode.

## Takeaways

- Put safety in **one gate** in the loop, not scattered across tools.
- Separate *hard rules* (always on) from *mode* (governs mutations).
- Denials should be **data the model can react to**, not crashes.
